# 仕様書 変更記録 — 静的配信への移行

**作成日** 2026-08-20
**対象** [`docs/kondate-spec.md`](kondate-spec.md) v1.0
**適用時点** Phase 2 の途中

---

## 0. この文書の位置づけ

仕様書 0.3 は、仕様に記載のない判断を実装者が勝手に決めることを禁じている。
以下は依頼者の指示を受けて仕様そのものを変更したものであり、**実装者の判断で
決めたものではない**。何を・なぜ変えたかを残すためにこの文書を置く。

仕様書本体は書き換えていない。差分はここに集約する。

---

## 1. 変更のきっかけ

依頼者から 2 点の要求があった。

1. **無償で運用したい**（AI 利用料・ホスティング料をかけない）
2. **Vercel での運用をやめ、GitHub Pages の静的配信に切り替えたい**

2 の理由は依頼者の言葉で次のとおり。

> やり取りがめんどくさいし、レスポンスが悪い。更に結局ログを提供しなければ
> ならず、こちらでセキュリティのチェックをする必要が多く、工数に見合っていない。

Vercel 本番で `/` がサーバ側例外（Digest: 4022048023）を返し、ローカルの
本番ビルドでは再現しなかったことが直接の引き金になっている。原因の切り分けに
依頼者がダッシュボードのログを都度取りに行く必要があり、この往復自体が
コストになっていた。**サーバを持たなければ、サーバ側例外は起きない。**

## 3. 各変更の根拠

### 3.1 ホスティング（2 章）

GitHub Pages は公開リポジトリなら無料で、実行環境を持たない。
配信は GitHub Actions のワークフロー（[`.github/workflows/pages.yml`](../.github/workflows/pages.yml)）が行う。

失うもの / 失わないもの：

| | Vercel | GitHub Pages |
|---|---|---|
| 費用 | Hobby は無料だが商用不可・上限あり | **無料** |
| サーバ側例外 | 起きうる | **構造上起きない** |
| 秘密情報の保管 | ダッシュボード | **不要になった**（サーバ秘密が無い） |
| Supabase との距離 | `hnd1` 固定で国内 | ブラウザ ↔ Supabase の直通。**むしろ 1 ホップ減る** |

非機能要件 2.1 の「週間献立の生成は 2 秒以内」は、生成が
ブラウザ上の決定論的計算になるため、ネットワーク往復が減る分だけ有利になる。

### 3.2 2.2-8 の解除 —— ここだけは慎重に扱う

禁止事項 2.2-8 の理由は「ロジックとレシピ DB が露出する」だった。
静的配信では献立生成をブラウザで動かすしかないため、この禁止と両立しない。

**仕様に合わせて実装を曲げるのではなく、目的に照らして仕様の方を直す**という
依頼者の指示に従い、禁止の前提が今も成立するかを確認した。

- **ロジックの露出** — このリポジトリは既に public である。生成アルゴリズムは
  仕様書 7 章に平文で書かれ、誰でも読める。**秘匿はもともと成立していない。**
- **レシピ DB の露出** — レシピは Supabase にあり、ブラウザは ANON KEY で
  アクセスする。他世帯の行は RLS が返さない。**露出量は Vercel 構成と同じ**で、
  Route Handler の有無で変わらない（Route Handler も ANON KEY 相当の権限で読む）。
- 利用者は招待済みの 2 名のみ。競合に模倣される類のロジックでもない。

したがって 2.2-8 が守っていた実体は無い。**解除する。**

一方で、**次の 4 つは解除しない。** これらは今も実体のある防壁である。

- 2.2-3 Service Role Key をアプリコードで使わない
- 2.2-4 RLS を有効化しポリシーを設定する
- 2.2-5 週間献立の生成に AI を使わない
- 2.2-1 サインアップ導線を実装しない

とくに 2.2-3 / 2.2-4 は、この構成で**唯一の認可境界**になった。
サーバが無くなった分、RLS の重みは増している。テーブルを追加するときは
RLS の有効化とポリシー設定を必ずセットで行う。

### 3.3 認証の保護方法（4.2）

ミドルウェアは Node ランタイムを要するため静的配信では動かない。
`app/(app)/layout.tsx` が `supabase.auth.getUser()` で判定し、
未ログインなら `/login` へ送る。`onAuthStateChange` を購読しているので、
ログアウトや別端末での失効にも追従する。

**これは「見せない」ための措置であり、防壁ではない。**
JavaScript を止めれば迂回できる。迂回されても Supabase から 1 行も返らない
のは RLS が効いているからで、そこが唯一の防壁である（仕様書 3.3）。

4.2 の「未認証は 401」も同じ理由で削除した。返す主体（Route Handler）が
存在しない。同等の役割は Supabase 側が担い、無効なセッションでの
クエリは PostgREST が 401 を返す。

### 3.4 AI の凍結（6 章・8 章・11.1）

`ANTHROPIC_API_KEY` は従量課金であり、「無償で運用したい」という要求と
両立しない。またサーバが無くなったため、鍵を安全に置く場所も無い
（2.2-2 により `NEXT_PUBLIC_` は付けられない）。

AI が担っていたのは次の 2 つで、いずれも代替がある。

| 用途 | 代替 |
|---|---|
| レシピ生成（8 章） | **手入力フォーム**（`app/(app)/recipes/recipe-form.tsx`） |
| 自由文のタグ変換（8.5） | Phase 6。チップ選択で置き換える |

**献立生成そのものは元から AI を使わない**（2.2-5）。ツールの中核価値は
無傷である。

8 章の仕様は削除せず凍結する。将来 AI を戻す場合は、Supabase Edge Functions
に置けばサーバ秘密を持てる（GitHub Pages を維持したまま実現できる）。

`zod` は依存関係に残している。8.4 が要求する AI 出力の検証で使うもので、
現在は未使用だが、外部ライブラリの出し入れは 0.3 の対象であり、
凍結中の機能のために抜き差しはしない。

### 3.5 draft 承認フローの扱い（5.2-8 / 2.2-6）

2.2-6「AI 生成レシピを `status='active'` で直接保存する」の禁止は、
分量の誤りが未検証のまま食卓に出ることを防ぐためのものだった。

手入力では、入力者が分量を確認した本人である。draft を経由する意味が無いため、
手入力レシピは `status='active'` で保存する。`draft` の値と承認フローの仕様は
残す（AI を戻したときにそのまま必要になる）。

### 3.6 シードの投入経路（11.1）

仕様書は `scripts/seed-recipes.ts` を実行して 20 件を投入する想定だった。
この構成ではサーバも実行環境も無く、次の経路がすべて塞がっている。

| 経路 | 塞がっている理由 |
|---|---|
| `scripts/seed-recipes.ts` | 実行環境が無い。開発機からしか動かない |
| Management API（`npm run db:seed`） | 個人アクセストークンが要る。アカウント全体の管理者権限を持つため預からない |
| SQL Editor に貼る | 520 行。依頼者はスマートフォン中心の運用で現実的でない |
| ANON KEY でログインして投入 | 招待済みアカウントのパスワードが要る |

そこで **レシピ画面に「はじめの20品を読み込む」を置いた。**
ログイン中のセッションをそのまま使うので、鍵もパスワードも動かない。
書き込みは RLS を通る（仕様書 2.2-3 を維持）。

これは仕様書 2.2-12「仕様にない機能を追加する」に触れる。ただし
**投入するデータそのものは 11.1 の指定どおりで、増えているのは経路だけ**である。
20 件が揃うとボタンは表示されなくなる。恒久的な画面ではない。

データは [`supabase/setup/seed-recipes.json`](../supabase/setup/seed-recipes.json) から読む。
これは `04_seed_recipes.sql` を PostgreSQL に流した結果を書き出したもので、
手では書いていない。SQL と画面から入る内容がずれない。

### 3.7 設定画面とホーム画面への追加（5.2-9 / 12 章）

依頼者の指示により、Phase 7 の設定画面を先に作った。仕様書 0.2 のフェーズ
分割に反するが、**世帯の値（人数・調理時間の上限・和洋中比率・アレルギー）は
Phase 3 の献立生成がそのまま読む**ため、生成に入る前に触れる形にしておくほうが
手戻りが少ない。

仕様書 5.2-9 に無いものを 3 つ足した。

| 追加 | 理由 |
|---|---|
| パスワードの変更・再設定 | 認証は Supabase 任せで、画面が無いと利用者が自分で直せない |
| ログアウト | 同上。2 名で 1 台を共有する場面がある |
| ホーム画面に追加 | 下記のとおり |

**ホーム画面への追加**（`app/manifest.ts` / `public/sw.js`）は仕様書に無い。
依頼者の指示による。仕様書 2.1 は「オフライン非対応」と定めているため、
**Service Worker は内容を蓄えない。** `fetch` をそのまま通すだけにしてある。
蓄えると配信し直しても古い画面が残り、前の構成で苦労した
「手元では動くのに本番が違う」を作り込むことになる。

アイコンは「献立」を縦に組んだもの。**画面の見出しと同じ Shippori Mincho B1**
で、アプリが自分で配っているフォントから描き出している。別途フォントを
持ち込むと、アイコンと画面で書体がずれる。

### 3.8 献立生成で補ったこと（7.1 / 7.2）

7.2 の擬似コードをそのまま実装すると、シード20件で週が組めない場合があった。
種を 1〜50 まで振って確かめたところ、次の 2 つが残った。

**同カテゴリの 3 日連続。** 7.2 のスコアリングは「前日と同カテゴリなら -20」
しか持たない。3 日目を防ぐ仕組みが無く、和食が 6 件を占めるシード構成では
実際に 3 日続いた。7.1 はハード制約なので、**前 2 日が同じカテゴリなら
その和洋中は候補の段階で外す**ようにした。点差ではなく候補から外す。

**大豆製品を週 2 回。** 7.2 の目標配分は主菜の大豆が 1 回。7.2-4 の副菜選びは
食品群だけを見るため、大豆の副菜（白和え）が選ばれない週が出て届かなかった。
**足りないぶんを大豆の副菜で補う**手当てを足した。

どちらも重み付けは変えていない（0.3）。判定の順序と、埋め合わせの手順を足した。

**副菜・汁物の重複。** 7.2-4 は「同スコアなら調理時間が短い方」としか
決めていないため、同じ副菜が 3 日続く週が出た。制約は満たすが食卓が単調になる。
**直前 2 日に出たものを避ける**ようにした。避けた結果ひとつも残らないときは
避けずに選ぶ。7.2 の主菜に `random(0,10)` が入っているのと同じ趣旨。

### 3.9 週間献立の操作（5.2-3）

5.2-3 は「長押し（PCは右クリック）で『この日を差し替え』」としている。
スマートフォンで長押しの導線は見つけられないため、**各日カードに
「差し替え」「固定する」「変える」のボタンを置いた**。押せる場所が見えている。

あわせて、**満たせなかったハード制約を画面に出す**ようにした。7.2-5 は
10 回試して駄目なら緩めてその旨を返す、としている。緩めたことを黙っていると
栄養の偏りに気づけないため、何が満たせなかったかと、どうすれば収まるかを書く。

### 3.10 週の起点と、週の切り替え（1.2 / 5.2-3）

仕様書 1.2 は「月曜始まりの7日間」としていたが、**日曜始まりに変える**。
依頼者の指示による。買い出しを日曜にまとめる生活に合っている。

影響したのは 2 箇所だけで、どちらも 1 行で切り替わる。

- `weekStartOf()` — 週の起点の求め方
- `isWeekend()` — 曜日別の調理時間の上限（7.1）。
  月曜始まりでは「5・6 番目が土日」だったが、日曜始まりでは
  **1 番目（日）と 7 番目（土）が休日**になる

生成アルゴリズム（7.2）そのものは曜日を直接見ていないため、変更していない。

あわせて **週を前後に切り替えられるようにした。** 仕様書は今週だけを
想定していたが、来週の献立を先に組みたい場面がある。プランは
`meal_plans` に週ごとに入るので、器はもとから週単位である。

### 3.11 固定と副菜の選択（5.2-3）

**固定は各日カードの右上の鍵ボタンにした。** 依頼者の指示による。
下段のボタンに混ぜていたが、押した状態が見えるほうが分かりやすい。
当たり判定は 44×44 px。

鍵は絵文字ではなく自分で描いている。端末によって形も色も変わるため。
**閉じているときは面で塗り（主色）、開いているときは線だけ**にして、
形と濃さの両方で違いが出るようにした。

ボタンの文言も直した。「差し替え」では何が起きるか分からないため
**「おまかせで選び直す」**に、「変える」は**「変更」**にした。
仕様書 5.5 は動詞で書くよう定めているが、「変更」は依頼者の指定による。

**副菜と汁物も手で選べるようにした。** 仕様書 5.2-3 の手動編集は
「レシピ変更・entry_type変更」としか書いておらず、実装では主菜だけを
選び直せる状態だった。副菜は食品群の埋め合わせで自動的に決まるが、
「今日は副菜をつけない」「これにしたい」を通したい場面がある。

「つけない」も選べる。仕様書 7.1 の緑黄色野菜や大豆の制約に触れる場合は、
「満たせなかった条件」に出る（3.9）。**黙って別の品を足し戻したりはしない。**

生成側には `fixedSides` / `fixedSoups` を足した。渡した日は自動で
選び直さないので、1 日いじっても他の日の副菜が入れ替わらない。

### 3.12 候補が尽きたときに止めない（7.2-2）

7.2-2 は、候補の主菜が 10 件未満なら**生成を断る**としている。
AI でレシピを増やせる前提の設計だが、実際にはこうなった。

> 主菜が9件しかありません。あと1件登録すると献立を作れます。

登録は 15 件ある。**先週使った 6 件が「14 日空ける」で外れていた。**
1 週間で 7 日ぶん使うので、主菜が 15 件でも翌週に残るのは 8 件しかない。
仕様書が想定する 12 件ならもっと早く行き詰まる。**構造的に毎週起きる。**

そこで、**同じ主菜を空ける日数を、候補が 10 件に届くところまで縮めて組む**
ようにした。縮めた事実は画面に出す。

> レシピが少ないため、同じ主菜を空ける日数を14日から3日に縮めました
> 主菜を増やすと、同じ料理が出る間隔を広げられます。

7.2-5 が「満たせない場合は緩和した上でその旨を返す」としているのと同じ扱いで、
**黙って条件を変えない**という点は守っている。

登録そのものが 10 件未満のときは、縮めても組めないので今までどおり断る。
そのときの文言は「候補」ではなく**登録されている総数**を出す。
「15 件あるのに 9 件しかないと言われる」という分かりにくさを無くすため。

### 3.13 配色の見直し（5.6）

仕様書 5.6 のトークンをそのまま使っていたが、**文字として読むには薄すぎる色が
混ざっていた。** 背景（`--paper` #F1F3EE）に対する比を測ると次のとおり。

| トークン | 元の値 | 背景との比 | 判定 |
|---|---|---|---|
| `--ink-3` | #909791 | 2.68 | 不足 |
| `--yuzu` / `--egg` | #C08A24 | 2.72 | 不足 |
| `--soy` | #6E8B5A | 3.41 | 不足 |

小さい文字は 4.5:1 が目安になる。`--ink-3` は日付・単位・見出しラベルに
広く使っており、いちばん効く。`--egg` と `--soy` は白文字をのせるので、
白との比も足りていなかった（3.04 / 3.82）。

**依頼者が気に入っている背景色は変えていない。** 色相と彩度も保ったまま、
明度だけを下げて必要な比を確保した。

| `--paper` 背景 | #F1F3EE | — | — |

7ファイルにあり、トークンの外にあった。仕様書 5.6 は「値はここが唯一の定義元」

オリーブ色の太い線になり、依頼者が気に入っている軽さが失われる。
**罫線は区切りの目印で、意味は文字と面が担っている**という判断による。

### 3.14 「未定」の日（5.2-3）

献立を組んだあと「この日はまだ決めていない」と置ける状態を足した。
依頼者の指示による。

`entry_type` の ENUM（cook / eatout / batch / leftover）には足していない。
**未定は「その日の行がまだ無い」状態として表す。** DB の型を変えずに済み、
読み戻したときも行の有無で復元できる。

未定の日は、

- 品を入れない。おまかせでも埋めない
- 週次の判定から外れる。品が無いことを理由に「緑黄色野菜がない」と言わない
- 揚げ物やカテゴリの連続を切る（あいだに何も無いため）
- 買い物リストに何も足さない

「自炊しない」とは別に置いている。外食は決まっている、未定は決まっていない。

### 3.15 買い物リストの数量を直せるようにする（5.2-6 / 9章）

仕様書 5.2-6 の買い物リストは、チェックだけができる。
在庫があって少なく済む日や、その日だけ多めに作る日があるため、
**数量を手で増減できるようにした。** 依頼者の指示による。

刻みは単位と今の値から決める。

| 条件 | 刻み | 例 |
|---|---|---|
| 単位が g / ml | 10 | 500g → 510g |
| 端数がある、または 1 以下 | **1/4** | 1と1/2個 → 1と1/4個 → 1個 → 3/4個 |
| それ以外 | 1 | 2切れ → 3切れ |

依頼者の指定どおり 4 分の 1 きざみにしてある。g と ml を 1 ずつにすると
250g を 300g にするのに 50 回押すことになるため、そこだけ 10 にした。

**表示も分数に変えた。** `0.75 個` ではなく `3/4 個`、
`1.5 大さじ` ではなく `大さじ1と1/2`。料理ではそのほうが読み取りやすく、
4 分の 1 きざみで押したときに値が素直に読める。
レシピ詳細の材料表示も同じ関数を使っているので、そちらも揃う。

分量が「適量」の材料は増減できない。数が無いものを数で動かせない。
ボタンは押せない見た目にしてある。

**注意** 週を再生成して確定し直すと、買い物リストは作り直される。
手で直した数量はそのとき失われる。献立が変われば要る量も変わるため、
そちらが正しい。

### 3.16 買い物を「かごに入れた」と「会計した」に分ける（5.2-6）

仕様書 5.2-6 の買い物リストは、チェックが1段階しかない。
実際の買い物はこう進む。

1. 週間献立を確定する
2. 店へ行き、かごに入れながらチェックしていく
3. レジで会計する
4. 週の途中でもう一度買い物に行く

この流れだと、1段階では次の2つが困る。

- **チェック済みが次の買い物で邪魔になる。** 買い終えた品が一覧に残り続ける
- **買えなかった品でチェックが埋まらない。** 品切れだった品と、まだ見ていない品の
  区別がつかない

そこで2段階にした。

| 状態 | 持ち方 | 画面 |
|---|---|---|
| 買うもの | — | 一覧に並ぶ |
| かごに入れた | `checked` | 取り消し線。2端末に即時同期（9章） |
| 買い終えた | `purchased_at` | 一覧から畳まれる。「買い終えた N 品」に入る |

**「会計した」を押すと、かごに入れた品だけが畳まれる。**
買えなかった品はチェックが付いていないので、そのまま次の買い物に残る。
特別な操作は要らない。

畳んだ欄は開けて、1品ずつ「戻す」で買うものへ返せる。

**列を1つ足した。** `shopping_items.purchased_at timestamptz`。
ENUM ではなく列の追加なので、既存のデータは変わらない
（[`supabase/setup/10_shopping_columns.sql`](../supabase/setup/10_shopping_columns.sql)）。

列がまだ無い間も一覧は開ける。取得は列を並べずに行い、
「会計した」を押したときだけ、何をすればよいかを画面に出す。

### 3.17 レシピ詳細の URL（5.2-4）

静的書き出しでは動的セグメント `/recipes/[id]` を事前生成できない。
レシピ ID は利用者が作るもので、ビルド時には存在しない。
クエリ文字列 `/recipe/?id=<uuid>` に変更した。画面の内容は変わらない。

### 3.18 買い物メモと、売り場ごとの折りたたみ（5.2-6）

3.16 で買い物を2段階にしたあと、店内での使い方をもう一段そろえた。

**手で品物を足せるようにした。** 牛乳・パン・洗剤のように、献立には出てこないが
同じ買い物で買うものがある。別のメモ帳に書くと二重管理になるので、
買い物リストに直接足せるようにした（品名・数量・単位・売り場）。

足した品には `shopping_items.is_extra` を立てる。
**週の献立を確定し直したときに消えないようにするため**で、
確定時の入れ替えは `is_extra = false` の行だけを消す
（[`app/(app)/week/page.tsx`](../app/(app)/week/page.tsx)）。
献立から作られた品と見分けがつくよう、一覧では「メモ」と印を付け、
手で足したものだけ × で消せる。

**売り場ごとに畳めるようにした。** 店内は売り場を順に回るので、
買い終えた売り場が画面に残り続けると、いま見る場所が探しにくい。
売り場の見出しを開閉ボタンにして、残り件数（全部かごに入れたら「済」）を出す。

畳む・開くの既定は**残り件数**で決める。買うものが残っていれば開き、
無くなれば畳む。手で開いたときはその状態を優先する
（`openState[category] ?? left > 0`）。
一覧が短くなっていくので、進み具合がそのまま画面に出る。

畳み方の状態は画面の中だけに持ち、保存しない。2端末で同期する必要は無く、
同期すると相手の店内の進み具合で自分の画面が畳まれてしまう。

`is_extra` の追加は 3.16 の `purchased_at` と同じファイルにまとめた
（[`supabase/setup/10_shopping_columns.sql`](../supabase/setup/10_shopping_columns.sql)）。
`purchased_at` と同様、列がまだ無い間も一覧は開ける。

### 3.19 買い物メモの売り場を品名から見当づける（5.2-6）

3.18 で足した「品物を足す」を二人で使ったところ、牛肉・鶏肉・豚肉が
そろって「その他」に入っていた。売り場の初期値が「その他」で、
選び直さないとそこに入る作りだったため。

店内を売り場順に回るのに、肉が「その他」に紛れると探せない。
初期値を品名から決めるようにした（[`lib/guess-shop.ts`](../lib/guess-shop.ts)）。

見当のつけ方は2段構え。

1. **食材マスタ**（11.2）に同じ名前があれば、その売り場。
   レシピの材料から作られる表なので、この家で実際に使う食材が載っている。
   決め打ちの語より確かなので先に見る。部分一致も拾う
   （「鶏もも肉 300g」と書いても精肉）。
2. 載っていなければ**語の手がかり**。上から順に見て最初に当たったものを採る。
   並び順が意味を持つ。「牛乳」は「牛」より、「ごま油」は「ごま」より、
   「切り干し」は「大根」より先に置く。

見当なので外れる。画面では初期値として出すだけで、足す前に選び直せる。
**一度手で選んだら、そのあと品名を直しても勝手に動かさない。**
どちらの状態かは欄の下に文で出す。黙って値が変わると、選んだつもりが
戻っていた、という事故になる。

食材マスタは「品物を足す」を開いたときに一度だけ読む。
普段の買い物では使わない表なので、一覧を開くたびに取りに行かない。
読めなくても語の手がかりだけで見当はつくので、失敗は画面に出さない。

**単位の書き方も揃える**（`normalizeUnit`）。同じ買い物リストに
「1 G」と「1 g」が並んでいた。全角を半角にし、g・kg・ml・cc は小文字、
L は大文字に寄せる。個・本・丁のような日本語の単位はそのまま残す。
入力欄から離れたときに直すので、直ったことが目に見える。

### 3.20 料理のリクエスト（5.2-7 / 7.2 / Phase 6）

仕様書 5.2-7 のリクエストは「自由文を AI でタグに変換し、確認画面を挟んでから
週を組み直す」もの。AI を凍結したため（変更記録 3.4）そのままは作れない。

依頼者が求めたのは、もっと直接的なもの——**献立から料理を選んで
「これが食べたい」と出し、それが献立と選び直す一覧の目立つところに出ること**。
自由文の解釈が要らないので、AI 無しで同じ目的を果たせる。

**表を分けた。** 仕様書 3.1 の `plan_requests` は `plan_id` に紐づく。
週が変わると消えるので、「今度これが食べたい」を持ち続けられない。
`recipe_requests` を新しく作り、世帯に紐づけた
（[`supabase/setup/11_recipe_requests.sql`](../supabase/setup/11_recipe_requests.sql)）。
献立に入って確定するまで効き続ける。

| 列 | 意味 |
|---|---|
| `recipe_id` | リクエストした料理 |
| `status` | `open`（まだ入っていない）／ `done`（入って確定した） |
| `requested_by` | 誰が出したか。二人で使うので出す |
| `fulfilled_at` | 叶った時刻 |

`open` のあいだは同じ料理を二重に出せない（部分ユニーク索引）。
叶ったあとなら、また出せる。

**生成での扱いは「押し上げ」であって「決め打ち」ではない。**
7.2 のスコアに `REQUEST_BONUS`（200）を足す。他の項目——たんぱく源の配分・
評価・食材の使い切り・ゆらぎ——を全部足しても届かない大きさにしてあるので、
候補に残っている限りその週に入る。

ただし 7.1 のハード制約は越えない。アレルギー食材を含む料理、
その日の調理時間の上限を超える料理、揚げ物の2日連続は、
リクエストされていても候補の段階で外れる。
**日を決める `fixedDays` とは別物**で、条件に合わない週には入らない。

押し上げは `build()` の中で必ず載せる。呼ぶ側で足す形にすると、
渡し忘れた経路だけリクエストが効かなくなる（実際に一度そうなった。
「今週の献立を作る」だけが `build({})` を呼んでいて、効いていなかった）。

**出す場所は2つ。**

1. **週間献立の上**。日カードより先、リボンより上に置く。
   入ったなら日付を、入らなかったなら「まだ入っていません」と書く。
   誰が出したかも添える。取り下げもここから。
2. **主菜を選び直す一覧の先頭**。「リクエスト」の印を付ける。
   並べ替えるだけで、同じ組の中の並びは変えない。

すでに週に入っている料理は先頭に出さない。選び直す先にならないため。

**叶ったら消える。** 週を確定したとき、その週に入っているリクエストを
`done` にする。行は消さずに残す。いつ何を食べたいと言ったかが分かるようにするため。
取り下げは行ごと消す。叶ったわけではないので、記録に残す意味がない。

リクエストを出せるのは**主菜だけ**。副菜と汁物は主菜の食品群を埋める形で
自動的に決まるので（7.2-4）、指名しても組み立てと噛み合わない。

表がまだ無いあいだも、レシピ詳細と週間献立はそのまま開ける。
リクエストを出そうとしたときだけ、何をすればよいかを出す。

### 3.21 食品群の自動判定と、緑黄色野菜の一覧（6章 / 7.1）

食品群は登録画面で手で選ぶものだった。入れ忘れると、
7.1 の「緑黄色野菜を毎日1品以上」がそのぶん狂う。
材料名から当てるようにした（[`lib/food-groups.ts`](../lib/food-groups.ts)）。

純粋関数で、Supabase を import しない（仕様書 2.3）。
語を含んでいたらその群、という手がかりを上から順に見る。
並び順が意味を持つ。「醤油」は「油」より、「かつお節」は「かつお」より、
「大根の葉」は「大根」より先に置く。

初期値として出すだけで、手で押せば変えられる。
**一度手で選んだら、材料を直しても勝手に動かさない**（「自動に戻す」で戻る）。
買い物メモの売り場（3.19）と同じ扱いにした。

**六群の分類から意図的に外したものが2つある。**

| | 六群での扱い | ここでの扱い |
|---|---|---|
| 砂糖・小麦粉・片栗粉・パン粉 | 5群（糖質性エネルギー源） | 数えない |
| にんにく・しょうが・みょうが | 4群（その他の野菜） | 数えない |

どちらも小さじ数杯・ひとかけしか使わない。5群として数えると
ほぼ全ての和食が5群持ちになり、4群も同様で、栄養の目安として
意味をなさなくなる。5群は主食（米・パン・めん・いも）だけを数える。

**緑黄色野菜の一覧を、登録画面の食品群の下に置いた。** 畳んであり、既定は閉じている。
3群かどうかは見た目では決まらないため、判定を疑ったときに引ける場所が要る。

- トマト・ピーマン・さやいんげんはカロテンが 600µg に届かないが、
  食べる量と回数が多いため慣例として含める（厚生労働省の扱い）
- ねぎは青い部分（万能ねぎ・青ねぎ）だけが3群。白い部分（長ねぎ）は4群
- のりは海藻なので2群。緑ではあるが緑黄色野菜ではない

一覧に載っている食材が全て3群と判定されることは単体テストで見ている。
一覧と判定がずれると、画面の説明が嘘になるため。

**シード20件の手書きの値と突き合わせた。16件が一致し、
残る4件は手書きのほうが漏れている**（味噌汁の長ねぎ、中華スープのごま油、
ムニエルのレモン）。カレーの5群は、材料に米が無いのに付いていた。
既存のレシピは登録時の値のままで、書き換えていない。
編集して保存し直すと自動判定の値になる。

### 3.22 材料の売り場も自動で入れる（6章 / 9章）

食品群（3.21）と同じ理由で、材料の売り場も品名から当てるようにした。
既定が「青果」のままで、油も醤油も青果として保存されていた。
売り場は買い物リストの並び順にそのまま効くので（仕様書 9章）、
間違ったまま貯まると店内で探せなくなる。

判定は買い物メモで使っている
[`lib/guess-shop.ts`](../lib/guess-shop.ts) をそのまま使う。
判定の置き場所を2つに分けると、片方だけ直す事故が起きる。

**買い物メモ向けの語彙では足りなかった。** レシピの材料には
調味料と粉類と香辛料が出てくる。シードの62品と突き合わせると
50件しか合わず、酒・豆板醤・カレー粉・ローリエ・鶏がらスープの素・
ししとう・レモンなどが漏れていた。足して 61/62 になった。

**小麦粉・片栗粉・パン粉を乾物ではなく調味料に置いている。**
買い物リストの「調味料を出さない」設定（9章）に一緒に従わせるため。
家にあるものを毎週リストに出しても仕方がない。

**残る1件は意図した違い。** カットトマト缶をシードは「その他」に
していたが、缶詰は乾物の棚にあるので「乾物」にした。店内で探しやすい。

行ごとに、手で選んだかどうかを覚える。**手で選んだ行は品名を直しても
動かさない。** 編集で開いたときは、保存されている値をそのまま使う
（以前に決めた売り場を勝手に塗り替えない）。

食材マスタ（11.2）も見る。この家で実際に使う食材が載っているので、
決め打ちの語より優先する。登録画面を開いたときに一度だけ読む。

あわせて `e.target.value as ShopCategory` を無くした。
仕様書 2.2-10 が `as` を禁じている。選択肢の一覧から引き当てる形に変えた。

### 3.23 副菜と汁物からもレシピへ飛べるようにする（5.2-3）

日カードで、主菜の名前だけがレシピ詳細へのリンクだった。
副菜と汁物はただの文字で、作り方を見るには一覧から探し直す必要があった。
献立を見ながら作るので、その日に作る3品はどれも同じように開けるべき。

「副菜なし」「汁物なし」はリンクにしない。飛ぶ先が無い。
文字色を薄くして、押せないことが見て分かるようにしてある。

指で押す前提なので、行の中でも上下に余白を取って 19px → 28px にした。
`inline-block` にしてあるので、料理名の途中では折り返さない。

### 3.24 買い物リストが古いことを画面に出す（5.2-6 / 9章）

「献立から消したはずのトマトが買い物リストに残っている」と報告があった。
追ったところ、原因は2つで、どちらも不具合ではなく**伝えていないこと**が問題だった。

**1. 買い物リストは確定を押したときの写し。**
`persist()` は `if (!confirmed) return;` で止まり、下書きのあいだは作り直さない。
買い物の途中でリストの中身が入れ替わらないようにするためで、これは意図した作り
（変更記録 3.16）。ところが献立を変えると `meal_plans.status` は `draft` に戻るのに、
買い物リストの画面は前の写しをそのまま出していた。**古いという表示が無かった。**

確定後に献立が変わっているとき、一覧の上に知らせるようにした。
`status !== "confirmed"` かつ品が並んでいる状態が、
「前に確定したときの写しを見ている」と正確に一致する。

作り直しの操作はここに置かない。組み立てには献立・レシピ・材料・食材マスタ・
世帯の設定が要り、週間献立の画面がすでに全部持っている。同じ組み立てを2箇所に
書くと、片方だけ直す事故が起きる。週間献立へのリンクだけを置いた。

**2. 同じ汁物が週に何日も入る。**
汁物は主菜の不足食品群を埋める形で決まるので（7.2-4）、
同じものが3日に入ることがある。実際に確かめた週では
卵とトマトの中華スープが 3 日に入っていて、トマトは 3 個と積まれていた。
**1日だけ別の汁物に替えても、残りの日から材料は消えない。**
これは組み立てとして正しい。
